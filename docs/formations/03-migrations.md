# 3. Les migrations

## Ce que c'est

Une **migration** est une classe PHP qui fait passer la base d'un état à un autre : créer une table, ajouter une colonne, en renommer une. Elle a deux méthodes : `up()`, pour avancer, et `down()`, pour revenir en arrière.

Les migrations sont versionnées avec le code, dans le dossier `migrations/`. Chaque base garde la liste de celles qu'elle a déjà jouées, dans la table `doctrine_migration_versions`.

## Pourquoi ça existe

L'entité décrit la table voulue ; il faut encore créer cette table dans chaque base qui fait tourner le code : la vôtre, celle d'une autre personne, celle de la CI, plus tard celle de la production. Et quand l'entité change, il faut modifier chaque table sans perdre les données qu'elle contient.

Une migration répond à ces deux besoins :

- **Elle se rejoue partout à l'identique.** Une base neuve reçoit toutes les migrations dans l'ordre, une base à jour aucune.
- **Elle se relit avant d'être jouée.** Le SQL est écrit dans un fichier, que l'on peut lire, corriger et faire relire, comme du code.

## Où le voir dans ce projet

- [migrations/Version20261113114813.php](../../migrations/Version20261113114813.php) : la seule migration, qui crée la table `note`.
- [config/packages/doctrine_migrations.yaml](../../config/packages/doctrine_migrations.yaml) : où sont les migrations.
- [src/Entity/Note.php](../../src/Entity/Note.php) : l'entité dont elle est tirée.
- [.github/workflows/ci.yml](../../.github/workflows/ci.yml) : le job `docker`, qui la joue sur un PostgreSQL neuf à chaque changement.

## Comment lire ce code

### Le fichier généré

Ouvrez [migrations/Version20261113114813.php](../../migrations/Version20261113114813.php).

```php
final class Version20261113114813 extends AbstractMigration
```

Le nom de la classe est la date et l'heure de sa création : 13 novembre 2026, 11 h 48 min 13 s. Les migrations se jouent dans l'ordre de ces noms, donc dans l'ordre où elles ont été écrites.

```php
public function up(Schema $schema): void
{
    // this up() migration is auto-generated, please modify it to your needs
    $this->addSql('CREATE TABLE note (id INT GENERATED BY DEFAULT AS IDENTITY NOT NULL, title VARCHAR(120) NOT NULL, content TEXT NOT NULL, created_at TIMESTAMP(0) WITHOUT TIME ZONE NOT NULL, updated_at TIMESTAMP(0) WITHOUT TIME ZONE DEFAULT NULL, PRIMARY KEY (id))');
}
```

`up()` contient le SQL à exécuter. Doctrine l'a écrit en comparant l'entité à la base, qui était vide : il manquait toute la table. Chaque colonne correspond à une propriété de `Note`, avec le type expliqué dans [la fiche 1](01-orm-et-entites.md) et détaillé dans [base-de-donnees.md](../base-de-donnees.md).

```php
public function down(Schema $schema): void
{
    $this->addSql('DROP TABLE note');
}
```

`down()` fait l'inverse : supprimer la table. On l'utilise rarement, mais elle doit exister et être juste.

Le commentaire `please modify it to your needs` est sérieux : **le fichier généré est un brouillon à relire**. Ici, il n'y avait rien à changer. Ailleurs, on corrige souvent. Par exemple, Doctrine ne sait pas toujours reconnaître un renommage de colonne : il peut écrire une suppression de l'ancienne colonne suivie de l'ajout d'une nouvelle, ce qui perdrait les données. On remplace alors ces lignes par un `ALTER TABLE ... RENAME COLUMN` écrit à la main.

`getDescription()` renvoie une chaîne vide. On peut y écrire une phrase, qui apparaît dans `doctrine:migrations:list`. Ce projet l'a laissée telle que générée.

### Où Doctrine range les migrations

Dans [config/packages/doctrine_migrations.yaml](../../config/packages/doctrine_migrations.yaml), écrit par la recette :

```yaml
doctrine_migrations:
    migrations_paths:
        'DoctrineMigrations': '%kernel.project_dir%/migrations'
```

Les classes du dossier `migrations/` ont l'espace de noms `DoctrineMigrations`, et non `App\...`. Ce n'est pas un oubli : comme le dit le commentaire du fichier, elles ne doivent pas être chargées comme le reste de l'application. Symfony ne les prend pas pour des services ; seul Doctrine Migrations les lit, quand on le lui demande.

### Le cycle de travail

Chaque changement de schéma suit les mêmes étapes :

1. Modifier l'entité, à la main ou avec `make:entity`.
2. Générer la migration avec `make:migration`.
3. **Lire** le fichier produit, et le corriger si besoin.
4. La jouer avec `doctrine:migrations:migrate`.
5. Vérifier avec `doctrine:schema:validate`.
6. Commiter l'entité **et** la migration ensemble.

Les commandes sont détaillées plus bas.

### Savoir où en est une base

Doctrine Migrations compare les fichiers de `migrations/` à la table `doctrine_migration_versions` de la base.

`doctrine:migrations:status` résume la situation. Sur une base neuve :

```text
|                      | Current              | 0                                                                      |
|                      | Latest               | DoctrineMigrations\Version20261113114813                               |
| Migrations           | Executed             | 0                                                                      |
|                      | Executed Unavailable | 0                                                                      |
|                      | New                  | 1                                                                      |
```

Une migration est disponible (`New`), aucune n'a été jouée (`Executed`).

`doctrine:migrations:up-to-date` répond par oui ou par non, et sert dans les scripts :

```text
 [ERROR] Out-of-date! 1 migration is available to execute.
```

Après `doctrine:migrations:migrate` :

```text
 [OK] Successfully migrated to version: DoctrineMigrations\Version20261113114813
```

```text
 [OK] Up-to-date! No migrations to execute.
```

Quand la base est en retard, `up-to-date` se termine avec un code d'erreur. Le job `docker` de la [CI](../ci-cd.md) s'en sert : si une migration manquait encore après `migrate`, l'étape échouerait.

`Executed Unavailable` compte l'inverse : des migrations jouées sur cette base, dont le fichier n'existe plus dans le projet. C'est le signe qu'une migration a été supprimée ou renommée après avoir été jouée, ce qu'il ne faut pas faire.

### Pourquoi pas `doctrine:schema:update`

Doctrine propose une commande plus directe : `doctrine:schema:update --force` compare l'entité à la base et applique la différence, sans fichier intermédiaire. C'est tentant, et c'est à éviter en dehors des tests :

- **Rien n'est écrit.** La modification n'existe que dans votre base. Une autre personne, la CI ou la production ne peuvent pas la rejouer.
- **Rien n'est relu.** Le SQL s'exécute tout de suite. Si Doctrine prend un renommage pour une suppression suivie d'un ajout, les données de la colonne disparaissent avant que personne ait pu le voir.
- **Rien n'est daté.** On ne sait plus dans quel ordre les changements ont eu lieu, ni lesquels une base a déjà reçus.

Les tests de ce projet font pourtant quelque chose de proche : [tests/ResetDatabaseTrait.php](../../tests/ResetDatabaseTrait.php) crée le schéma avec `SchemaTool`, la classe qui fait aussi tourner `schema:update`. Là, c'est le bon outil : la base de test est jetable, recréée à chaque test, et ses données n'ont aucune valeur. La [fiche 7](07-tests-avec-base-de-donnees.md) l'explique.

### Une migration est écrite pour une seule base

Relisez le SQL de `up()` : `GENERATED BY DEFAULT AS IDENTITY` et `TIMESTAMP(0) WITHOUT TIME ZONE` sont du PostgreSQL. SQLite ne les comprend pas. Doctrine a écrit ce SQL pour le moteur auquel il était connecté au moment de `make:migration`, ici PostgreSQL 16.

Une migration n'est donc pas portable : elle vaut pour le moteur de production, et pour lui seul. C'est pourquoi :

- `make:migration` se lance contre PostgreSQL, avec `symfony console`, et jamais contre la base de test SQLite ;
- les tests ne jouent pas les migrations, mais créent leur schéma avec `SchemaTool`, qui écrit le SQL de SQLite ;
- la migration elle-même est vérifiée par le job `docker` de la CI, qui la joue sur un vrai PostgreSQL.

Pour la même raison, la recette fixe `serverVersion` : deux versions de PostgreSQL peuvent produire un SQL différent, et la migration doit correspondre à celle de l'image.

## Commandes officielles utilisées

```bash
docker compose up -d --wait database
```

Démarre PostgreSQL. `make:migration` en a besoin : il compare l'entité à la base réelle.

```bash
php bin/console make:migration --help
symfony console make:migration
```

Génère une migration avec la différence entre les entités et la base. Si rien ne diffère, la commande le dit et ne crée aucun fichier. `symfony console` fournit l'adresse de la base, voir [la fiche 2](02-connexion-et-postgresql.md).

```bash
symfony console doctrine:migrations:migrate
```

Joue les migrations qui manquent. La commande demande confirmation ; `--no-interaction` répond oui à votre place, comme le fait la CI.

```bash
symfony console doctrine:migrations:status
symfony console doctrine:migrations:list
symfony console doctrine:migrations:up-to-date
```

L'état général, la liste détaillée avec les dates d'exécution, et la question « est-ce à jour ? ».

```bash
symfony console doctrine:schema:validate
```

Vérifie le mapping, puis compare la base au mapping. Deux `[OK]` veulent dire que le mapping est valide et que la base lui correspond. Seul `doctrine:migrations:up-to-date` dit qu'aucune migration n'attend d'être jouée.

```bash
symfony console doctrine:migrations:migrate prev
```

Revient d'une migration en arrière, en jouant son `down()`. Utile pour corriger une migration que l'on vient d'écrire, jamais sur une base qui contient des données utiles.

## À retenir

- Une migration est une classe datée, versionnée avec le code, qui fait évoluer le schéma.
- Le fichier généré par `make:migration` est un brouillon : on le lit avant de le jouer.
- `doctrine_migration_versions` dit à chaque base ce qu'elle a déjà reçu.
- `doctrine:schema:update` modifie une base sans laisser de trace : à réserver aux tests.
- Une migration est écrite pour un moteur ; ici PostgreSQL, et elle est vérifiée sur PostgreSQL par la CI.
- On commite l'entité et sa migration ensemble.
